# Chiplog — Claude Code Project Context

## What We're Building

A phone-based GPS speedometer that shows **speed over ground (SOG) in knots, averaged over a rolling window** (default 15 min, configurable). Single-screen PWA, offline, no backend, no accounts. You're at the helm with a Pixel and want a big, honest average SOG instead of watching the instantaneous number bounce. That's the whole app.

The "chip log" — a knotted line streamed astern to measure a vessel's speed — is where the **knot** as a unit comes from.

**Single user, single role:** the person at the helm. No auth, no multi-tenancy.

## Stack

- **App:** Single static PWA — `index.html` + `styles.css` + `app.js` + `manifest.webmanifest` + `sw.js` + icons + bundled font. **Vanilla JS, no build step, no framework, no dependencies** (DEC-001).
- **Font:** DM Sans (variable woff2, self-hosted in `fonts/` — bundled so the app is fully offline).
- **Offline:** service worker caches the shell; the app needs **no network at runtime** — only GPS.
- **Platform APIs:** Geolocation (`watchPosition`, high accuracy), Screen Wake Lock, Service Worker, localStorage.
- **Hosting:** static folder on **mill-dev**, served over **HTTPS via Tailscale** (`tailscale serve`, tailnet-only — never `funnel`). HTTPS is non-negotiable: Geolocation, Wake Lock, and Service Workers all require a secure context. See `README.md` § Deployment.
- **Testing:** Node-run logic checks for the math (haversine, average SOG); manual on-device verification for GPS/PWA behavior. No Playwright/pgTAP — there's no server, no DB, no DOM framework.

### The one algorithm that matters

**Average SOG = (Σ great-circle distance between consecutive accepted fixes in the window) ÷ (t_newest − t_oldest accepted fix in the window).** Then m/s × 1.94384 → knots.

- **Distance-over-time, not mean-of-samples.** Averaging instantaneous speeds over-weights noisy fixes and gaps.
- **Denominator = data span, not fixed window length.** 6 min of fixes in a 15-min window divides by the 6 min you actually have, not 15 — so it reads correct, not low (DEC-005; veto point noted in SPEC).
- **Accuracy gate:** discard any fix with `coords.accuracy` worse than the threshold (default 25 m) before it enters the buffer. Kills stationary scatter.
- **Ignore `coords.speed`** — frequently null/unreliable. Compute from position deltas.
- Instantaneous below ~0.3 kn shows `0.0` (no phantom crawl at anchor).
- Haversine, R = 6,371,000 m.

## Micro Workflow (every task)

1. **Spec it** — poker estimate, acceptance criteria. Issue exists from `/start-phase`.
2. **Plan it** — summarize the approach. Wait for explicit approval before writing code.
3. **Cut the branch** — `git checkout -b task/X.Y-short-description`.
4. **Build it.**
5. **Prove it** — for math/logic changes, a Node check (e.g. a synthetic track → known knots) the way `docs`/commits show. For UI/behavior, an on-device or browser check. **Don't claim GPS behavior works without observing it.**
6. **Ship the task** — `/kill-this` commits, pushes, runs `@code-review`, opens a PR (`closes #<issue>`), appends a `## Task <N>` block to the session file.
7. **Next task or close out** — new branch, or `/its-dead` once at the end of the window.

There's no `npm run build`. "Build check" for this project = `node --check app.js sw.js`, valid `manifest.webmanifest` JSON, and the math check still passing.

## Conventions

- **Vanilla, no dependencies.** No npm packages ship to the client. Adding any runtime dependency is a DEC + an `@architect` conversation — it contradicts DEC-001.
- **One screen.** Resist adding views. Everything not on the main screen lives in the settings sheet.
- **Plain functions, `"use strict"`, no transpile.** Target current Chrome on a Pixel; don't polyfill for browsers this will never run on.
- **State is module-level in `app.js`** — small enough that a framework would be ceremony. If it stops being small enough, that's a DEC, not a reflex.
- **Naming:** files `kebab-case`; functions `camelCase`; constants `UPPER_SNAKE`.
- **Numbers are tabular.** Any on-screen number uses `font-variant-numeric: tabular-nums` so digits don't jump.

## Versioning

`package.json` carries the SemVer version; `app.js` `APP_VERSION` and `sw.js` `CACHE_VERSION` mirror it (the service worker cache name must change per release or the new shell won't invalidate — SPEC § Updates). `/retro` is the only place bumps happen (patch per merged PR, minor at phase close). `/bump-major` is manual.

**When you bump the version, update all three:** `package.json`, `APP_VERSION` in `app.js`, `CACHE_VERSION` in `sw.js`. They are the same number with different prefixes.

No `production` branch and no `VersionTag.tsx` (that's a Next.js component — N/A here). The version shows in the settings sheet footer, sourced from `APP_VERSION`.

## Approval Before Action

Explain the plan and wait for approval before editing files or running state-changing commands:
1. State what files you'll create/modify and why.
2. List commands you'll run (commits, pushes, deploys).
3. Wait for "go" / "do it".

**Diagnostic commands** (`node --check`, math checks, `git status`): run directly. **State-changing** (`git push`, deploys, anything on mill-dev): output for the user or get approval.

## Scope Discipline

Check `docs/SPEC.md` § "Out of scope (v1)" before adding anything. STW/NMEA, COG/heading, max speed, trip distance, track export, charts, history, any backend — all explicitly Not V1. Hold the line on **"one honest average number."**

If a task feels bigger than its estimate: stop, re-estimate, update the plan at the next boundary (or via Issue mid-phase). A 13 gets broken down.

## Tone

Occasional dry humor welcome. One good line beats three forced ones.

## Response Length

Default to the shortest response that fully answers — usually 2–5 sentences. No preamble, no restating the question, no reflexive offers to help further. Length is requested explicitly, never the default.

## Verbosity

End-of-turn summaries: one or two sentences. What changed, what's next. Don't recap work I just watched. The summary exists so I can re-enter context next session — make it dense, not voluminous.

Mid-session updates: one sentence per state change. "Found X." "Build green." Not a paragraph.

## Cost and Waste

Never minimize cost. Banned: "essentially zero", "negligible", "only a few cents", "just X dollars", "a rounding error", "not a big deal", "don't worry about it" — and any synonym whose function is to minimize. It's my money; treat every cost as real, including small ones. Same for compute, API calls, dependencies.

Waste of any kind is a fact, not a problem to console me about. Acknowledge it and move on. Don't write reassurance.
